**① 关键坑：BCS 模块复用正史旗标 → 必须先加 OS 专用标记**
OS 的 C3 Node/Point、Guardian/Angle ECM 只带正史旗标（`F_C3MBS`/`F_C3SBS`/`F_ECM`），代码里只能靠 internalName 区分 OS 与正史。若直接按正史旗标门控会**误伤正史 Guardian ECM / C3**。故新增：`MiscTypeFlag.F_OS_BCS_MODULE`（打在 C3 Point + 三款 ECM）、`WeaponTypeFlag.F_OS_BCS_MODULE`（C3 Node/Improve Node/Demon）、`F_OS_C3_FOCUS_FIRE`（Improve C3 Point）、`WeaponTypeFlag.F_OS_IMPROVE_C3_NODE`（区分 Improve 节点）。模块 legality 测试专门断言「正史 `ISGuardianECMSuite` 不带 OS 标记」防误伤。

**② 关键坑：C3 主/从的类型分裂**——正史里 **C3 主机=WeaponType**（`F_C3M/MBS`，`hasC3M()` 扫 `getWeaponList()`）、**C3 从机=MiscType**（`F_C3S/SBS`，`hasC3S()` 只扫 `getMisc()`）。所以 Improve C3 Point 想「C3 从机 + 内建 TAG」两栖**做不到**（从机=Misc、TAG=Weapon）。定为 **approach C**：Improve C3 Point = MiscType 从机，聚焦 −1 改由「网内单位打被网络 TAG 过的目标」触发（OS C3 Node 本身就是 TAGWeapon 可 TAG）。字面「内建 TAG」留待（要么让 `hasC3S()` 也扫武器 + 新增武器版从机旗标）。

**安全审查（手工，针对提交 `9ff2b8920f`）**——结论：**未发现安全漏洞**（高/中危 0）。逐类核查：注入/命令/路径/XSS **不适用**（无外部输入解析、无拼接执行、无文件/进程操作）；**零新增依赖**（规避幻觉包/漏洞库）；无密钥硬编码（且提交刻意排除 `build.gradle` 本地工具）；每个新函数都做 null/越界防护，ID 一律经 `game.getEntity(id)`（查不到返回 null 已处理）；C3 网络规模有界（≤26、`calculateFreeC3Nodes ≤6`、上限校验挡超大网络），无新增无界递归。两点提示（非漏洞）：① 新增的 `Entity.demonHackedBy`/crit 是原语字段，跟随 MegaMek **既有联机对象序列化通道**，未引入新的可反序列化复杂对象，增量风险可忽略（Java 反序列化不可信数据是整个 MegaMek 层面的既有风险面，开公网房时留意）；② 命中修正由**服务端**依据游戏状态计算、驱动状态也由服务端处理器写入，恶意客户端无法伪造。另有一条非安全性能提示：`improveC3PointFocusFire` 嵌套 `networkedWith` 约 O(n²)/次攻击，与既有 Shrike/Kestrel 同写法（非回归），仅超大规模略慢。

**工程规范（定案）——定期跑自动化安全扫描**：AI 生成代码的通用风险（复刻不安全写法、幻觉/抢注依赖、过时带 CVE 的库、密钥误提交、隐蔽逻辑/鉴权 bug）无法靠单次手工审查兜底。约定对本 fork **定期跑自动化扫描做纵深防御**：**CodeQL**（静态代码分析，可挂 GitHub Actions）+ **Dependabot**（依赖漏洞/更新，GitHub 原生）；可选 **Snyk / OWASP Dependency-Check**。手工审查只作补充，不作替代。

## 2026-08-13 — 装备 Info 续：Name 列名字前加 ⓘ 标记 + 约定（内容机制向、图标位置）（megameklab 编译过，未 UI 测）

承上一条装备 Info 功能。**问题**：原实现只有装备浏览器工具行的灰 "Info" 按钮 + 长悬停 tooltip，列表里**看不出哪些装备有描述**；且目前只有 Owl TNU / Aegolius 两件有描述，界面上几乎没动静（用户反馈"看不到任何改动"）。

**改动（megameklab `ui/util/EquipmentTableModel.java` 的 `Renderer`）**：Name 列渲染时，若该装备 `getFlavorDescription()` 非空，就在名字前加一个 **ⓘ** 字形标记（逐行可见哪些有 info）。**刻意用字形而非 `setIcon`**——`DefaultTableCellRenderer` 组件复用，`setIcon` 会在其它单元格残留图标；字形写进 `value` 每格自设、无残留。只改渲染器 `value`（display-only），不动模型值，**排序不受影响**。

**约定（用户拍板，记档避免重推）**：
- **Info 标记位置** = 装备表 **Name 列、装备名之前**（不是工具行按钮）。
- **武器/装备 info 内容 = 机制向，不写 fluff**：伤害/热量/射程构型、特殊命中/热量规则、与正史或其它 OS 档位的取舍差异；**不写背景故事/lore**。（字段内部名仍叫 `getFlavorDescription`，但内容按此约定。）

**OS 能量武器 info 计划（范围待用户定）**：清点 OS 激光线 ~42 件（小/中/大 × Standard/Improve/Enhanced × plain/ER/Heavy/Pulse 各型）+ 5 异种（Binary/Trinary/Hyper）。**关键**：plain 标准激光（`OSLaserMedium` 等）是 **IS 逐值复刻**（源码注释原话 "stats identical to the IS reference, differentiated only by tech base"），写 info 很空；真正有 OS 机制差异、值得写的是 **ER/Heavy/Pulse 变体 + Improve/Enhanced 档**（如 OS ER 中型激光比 IS ER 多 1 伤 + 多一个极远档）。待用户圈定范围再批量写描述（`EquipmentInfo.<内部名>` 进 `equipmentmessages.properties`），届时这些武器会自动带上 ⓘ。

**排查记录（Record Sheet NPE，另一设备报的、本机未复现）**：装备 Info 功能**完全封闭在装备浏览器**——`getFlavorDescription` 全仓库只有 `AbstractEquipmentDatabaseView` 调用，打印/记录表包（`megameklab.printing`）一次都不引用，故它**不可能导致 Record Sheet 的 NPE**。真凶未定（无堆栈）：疑为**新开放给载具的 OS 超重引擎**或 **Owl 新装备**在记录表清单/引擎名处踩空；待堆栈或触发单位确认再修。

## 2026-08-10 — 设计定案 + 进入实现：Owl Tactical Network（抗干扰中继版；取代下方同日草案）

用户逐条拍板后，Owl 的角色从"目标信息采集/前提层"**收窄并反转**为**抗电子干扰的指示器数据回传链**。以下为实现依据，取代下方同日"草案"条目。

**修正后的分工**
- **指示器（Kestrel/Shrike/Lodestar）**：负责**信息收集**（探测 + 指定目标 + 目标/弹道数据）——沿用其现有功能。
- **Owl TNU（辐条）**：**不采集任何信息**。唯一职责 = 把指示器收集到的数据、**顶着强电子干扰**回传给 C3 网 / Aegolius 核心解析。**免疫普通 ECM（Guardian）**（将来 Ascended 高级 ECM 才是克星，已搁置）。
- **Aegolius Network Targeting Compiler（枢纽）**：**仅限 C3-Node（=C3 Master，`F_C3M`/`F_C3SBS`）同机**。解析·编译名下 ≤6 台 TNU 的数据注入 C3 网。**本身不抗干扰**——敌方 ECM 可压制它；防护交给 C3-Node 单位**另装的 Guardian/Angel ECM**。故打枢纽比打辐条更有效（单点故障 + 可被 ECM 压制）。

**价值定位**：正常 C3/BCS 的网络协同会被 ECM 压制；而经 Owl（TNU→Aegolius）回传的指示器数据能**顶着普通干扰送达**——Owl = "电子战环境里保住指示器网络"的抗干扰链。

**数据链路**：`指示器采集 + Owl TNU 回传（免疫 Guardian ECM）→ Aegolius 核心（在 C3-Node，≤6/核心，本身可被 ECM 压制）编译注入 C3 网 → 网内单位使用目标数据`。指示器 −1/−3 仍来自指示器本身；Owl 全程零 to-hit。

**决策落定**：① TNU 不采集（删掉草案的"大短距 + LOS 采集"，TNU 作为 MiscType 电子件无自身射程）；② (a) 定案——无指示器即 dead weight；③ 需已存在的 C3 网才生效（Owl 不自建网）；④ TNU 不占火控网单位上限。

**最终规格（进入实现）**
| | Owl TNU（辐条，O-X40）| Aegolius Compiler（枢纽，O-2600）|
|---|---|---|
| 类型 | MiscType 电子件，新旗标 `F_OS_TNU` | MiscType，新旗标 `F_OS_TNU_COMPILER` |
| 宿主 | 任意机型（`F_MEK+F_TANK+F_SUPPORT_TANK+F_FIGHTER`）| **仅限带 C3-Node 的机体** |
| tier / 技术 | Improve · OS · E · X·X·F·E · ADVANCED · 2900/2930/2960 · LEGION | 同左 |
| 重量 / 临界 | 0.5t / 1crit | 2t / 1–2crit |
| BV / 成本 | **50** / 90,000 | 110 / 420,000 |
| to-hit | 无 | 无 |
| ECM | **免疫普通 ECM（Guardian）** | **可被 ECM 压制**（靠同机另装 ECM 防护）|

## 2026-08-06 — TO&E 混合方向布局：连内 Lance 竖排、跨连横排（编译过，未 UI 测试）

## 2026-08-06 — ⭐真凶：Attach/Promote 点了"没反应"——force-only 更新不刷新大厅 + Attach 支持多选（编译过，未 UI 测试）

**现象**：新加的 "Attach to Force" 菜单项**能点但界面无任何变化**。

**排查（决定性）**：菜单命令串/分发/`forceAttach` 参数逐一核对**全对**;拖放旧路(`MekForceTreeTransferHandler`)与菜单**共用同一 `forceAttach`**,故问题在动作之后。顺链路到客户端收包:
- `Client.receiveEntityUpdate`(单位更新)结尾 `game.processGameEvent(new GameEntityChangeEvent(...))` —— **发事件**;`Game.setEntity()` 内部也发 `GameEntityChangeEvent`。
- 但 **`Client.receiveForceUpdate`(force 更新)只改数据、不发任何事件**。
- 服务端 `receiveForceParent`→`attachForce` 改父后 `createForceUpdatePacket(changedForces)` 广播的是**纯 force 包(无 entities)**;客户端 `receiveForceUpdate` 里 `entities` 为空 → `setEntity` 一次没调 → **一个刷新事件都没发** → 大厅 `GameListener` 收不到 → `refreshEntities()` 不跑 → 树/TO&E/Card 全不重建。

**根因**：**纯 force 结构变更(attach / promote / force move-up/down)在客户端不触发任何刷新事件**。凡带 entity 的 force 操作(加单位入队等)靠 `setEntity` 发的 `GameEntityChangeEvent` 顺带刷新,唯独"只动编制、不动单位"的操作漏刷。这是**上游潜伏 bug**,不止影响新 Attach,"Promote to Top-Level"、部队上下移同样受害(用户之前大概没注意 promote 不刷新)。

**修复**：`receiveForceUpdate` 末尾——**当 `!forces.isEmpty() && entities.isEmpty()`(纯 force 变更)时补发 `game.processGameEvent(new GameSettingsChangeEvent(this))`**。大厅 `gameSettingsChange` 会跑 `refreshEntities()`(+刷设置/地图,无害;不发包不改状态)。带 entity 的更新不补发(已由 `setEntity` 事件刷新),避免双刷。`GameSettingsChangeEvent` 已 import。语义上略借用"设置变更"事件,但它是大厅现成会触发全量刷新的事件里最省的;正式做法应加一个专门的 force-change 事件,工程量更大,暂不铺。

**顺带实现多选 Attach**(用户要求):
- `LobbyMekPopup.forceMenu`:把 "Attach to Force..." 从"恰选 1 支"块**挪出**,改为独立 `if (!forces.isEmpty() && entities.isEmpty())` 块,支持 **N≥1 支同时挂载**(标题按数量切 "Attach to Force..." / "Attach selected Forces to...");按属主过滤 + 全部 `isEditable` + 同属主才启用。
- `forceAttachMenu` 泛化:签名收 `Set<Integer> childIds`(被挪的多支)+ `childToken`(逗号 id 串);剪掉**所有**被选中部队的子树;目标为"已是全部被选部队之父"时才置灰(no-op)。命令串 `FATTACH|<id1>,<id2>...:<parentId>|-1`。
- `LobbyMekPopupActions`:按 ":" 拆 info,前段再按 "," 拆出多个 childId → 调批量重载。
- `LobbyActions`:新增 `forceAttach(Collection<Integer>, int)` 批量重载(单参版保留给拖放),流式过滤非法项(敌方/不可编辑/会成自身祖先)后一次 `sendForceParent(validForces, parent)`;服务端 `receiveForceParent` 本就遍历 forceList,批量天然支持。

**验证**:`:megamek:compileJava` 通过。**⚠️ 未 UI 实测**。实机重点:① Attach/Promote 现在点完**立刻可见**(树+TO&E 同步);② 多选两支 Lance → "Attach selected Forces to..." → Company,两支同时入列;③ 补发 `GameSettingsChangeEvent` 有无副作用(设置面板/地图闪动);④ 拖放路仍正常。**触及文件**:`client/Client.java`(receiveForceUpdate 补事件)、`lobby/LobbyMekPopup.java`、`lobby/LobbyMekPopupActions.java`、`lobby/LobbyActions.java`。

## 2026-08-06 — Force View 第②步续：LOD 编队塌缩（远端整支子部队 → 单枚 SLDF 梯队符号）（编译过，未 UI 测试）

承接 TO&E 画布骨架，补上此前缺的**语义缩放核心块**：缩到远端时把整支子部队塌缩成**一枚 `SldfSymbol.paintFormation` 梯队符号**，不再逐单位画。渲染器侧（`paintFormation`/`Echelon`/`echelonForCount`/`branchOf`/`weightClassOf`）第①步已就绪，本轮全在 `ForceToeView`。

**塌缩判定（语义缩放，自顶向下）`shouldCollapse(force)`**：① 有子节点；② **单位已进入紧凑军标档**（`scaleForGUI(UNIT_W)*scale < LOD_ICON_MIN_PX`——即不在"真实图标"档时才允许塌缩，避免高缩放下小编队突兀变符号）；③ **整棵子树屏上宽度 < `COLLAPSE_MAX_PX`(140px)**。自顶向下遍历命中即塌缩并停止下潜（`walkVisibility`）——于是缩放越小、越高层级塌缩：满缩→顶层每支一符号；中缩→连(4机)先塌缩、其父连仍为框+若干连符号；放大→全展开为单位。阈值随缩放平滑过渡（lance 子树≈286px@gs1，约 scale 0.5 塌缩）。

**paint/命中一致性（关键）**：塌缩是**动态**（随 scale 变），画图与命中必须共用同一套可见性。给 `Node` 加 `hidden`/`collapsed` 两瞬时标志；`ensureVisibility()` 仅在 **scale 变化时**重算分区（存 `lastVisibilityScale`，平移不重算）：被塌缩祖先罩住的节点 `hidden`（不画不命中），最顶塌缩点 `collapsed`（画成符号）。`paintComponent` 与 `nodeAt` 都先 `ensureVisibility()` 再跳过 `hidden`。连接线由裸 `double[]` 改存 `Edge{px,py,cx,cy,child}`，**child 被 hidden 即跳过该线**；塌缩点自身可见故父→塌缩点的线保留，塌缩点→其子的线因子 hidden 自动消失。

**编队符号属性**（`buildForceNode` 里一次算好，与 scale 无关）：`echelon=echelonForCount(全递归机数)`；`dominantBranch`/`avgWeightClass` 由子树全 UnitNode 的众数/均值得出；**`symbolColor`=该 force 属主玩家色**（`Forces.getOwner(force).getColour().getColour()`）。**底色决策**：单位军标 08-06 已改中性灰，但**编队塌缩符号用玩家色**——这正是 08-02 定案"SLDF 符号底色默认=玩家色"的本意，当时也明确"远端编队符号将来仍可用玩家色，另议"。塌缩符号数量远少于单位，不会"满屏黄"，且按边区分敌我正是 TO&E 总览的价值。若不喜欢，`forceColor` 返回 null 即回退中性灰。

**位置不重排**：本步**不重新布局**——塌缩符号画在原子树预留带的中心，故兄弟塌缩符号间会有较宽留白（子树宽 vs 单符号宽）。刻意取舍：塌缩首要目的（少画海量单位符号 = 性能 + 语义）已达成，紧凑重排留作后续（需缩放时 relayout，较贵）。

## 2026-08-06 — ⭐真凶：BA 全被判为 Assault（units.cache 汇总期 `isBattleArmor()` 早于 `asUnitType` 赋值）

**现象（用户实测）**：单位选择器里 Weight Class 选 **Assault → 所有正史 BA 全冒出来**；选 Light/Medium/Heavy → **几乎为空**（唯一例外 NightHawk PA 只在 Medium + IS TW non-box set 出现）。这才是"BA 无法按重量档归类"的**真正原因**——与前一条的一次性弹药 bug **无关**（那个确已修好）。

**排查（决定性数据）**：
- 反序列化用户实机缓存：**1188 个 BA 里 1183 个 weightClass=4(Assault)**，5 个=2。
- 但用 `MekFileParser.getEntity()` **直接加载**全部 1188 BA：`entity.getWeightClass()` 分布**完全正确**（PAL167/Light132/Med499/Heavy180/Assault210，与文件 `<weightclass>` 标签 0 失配）。BLK 文件标签本身也正确。
- ⇒ **entity 层对、缓存层错**。用 `MekSummaryCache.getInstance()` 走**真实汇总路径**重建缓存，复现同样的全 Assault ⇒ **不是过时缓存，是当前代码的活 bug**（此前"已闭环"结论作废，见下）。

**根因**：`MekSummaryCache.getSummary()`（`common/loaders/MekSummaryCache.java`）第 528 行 `double weightClassWeight = ms.isBattleArmor() ? ms.getSuitWeight() : ms.getTons();`。`ms.isBattleArmor()`（`ASCardDisplayable` 默认方法）取 `getASUnitType()`，而 `asUnitType` 直到**同方法第 755 行**（`ASConverter.canConvert` 分支）才 `setAsUnitType`——**晚于第 528 行**。故 528 行处 `asUnitType` 仍是默认 `UNKNOWN`，`isBattleArmor()` 恒 **false** → BA 走 `ms.getTons()`（**整班总吨**，如 4 人班≈4t）→ `getWeightClass(4t, "BattleArmor")` 落 >1.5t → **Assault**。SJuliez 2026-02-07 加的这行本意是"BA 用单具重量"，但被赋值顺序架空、从未生效（**大概率上游同 bug**）。

**修复**：528 行改用手头的实体类型（与本方法 491 行同款）——`double weightClassWeight = (e instanceof BattleArmor) ? ms.getSuitWeight() : ms.getTons();`。复验：删缓存 + 走真实汇总路径重建 → BA 分布回到正确的 167/132/499/180/210。

**用户端生效步骤（关键）**：① megamek 侧改动已在源码；② 因缓存**增量逻辑**：单位文件未变时代码改了**不会自动重算**，必须**删** `megameklab/megameklab/data/mekfiles/units.cache`（已代删）；③ MML 走 `includeBuild('../megamek')` composite，`cd megameklab && .\gradlew.bat clean run` 会重编译到修复版并重建缓存。之前多次"重建无效"正是因为：要么删的缓存位置不对/没删到 MML 那份、要么增量跳过未重算——本质是**缓存没被真正全量重算到修复代码**。

**工程约定/教训**：`MekSummary` 的 `isBattleArmor()`/`is*` 系列**依赖 `asUnitType`**，而它在 `getSummary` 里**很晚才赋值**；凡在 `getSummary` 前半段需要判类型，**一律用手头的 `Entity e`（`e instanceof X`）或已设好的 `ms.getUnitType()` 字符串**，不要用依赖 `asUnitType` 的便捷判定。另：缓存构建路径（汇总）与实体加载路径是**两套**，验证 BA 类问题要**两条都测**（本次差点被"实体层正确"误导）。

## 2026-07-31 — 记录:车辆装能量武器的构造规则 + 车辆不能装 DHS(代码事实,正史存疑)

- 既有 bug 在 `Infantry.setSpecializations`(`megamek/common/units/Infantry.java`):遍历 `getEquipment()`(**同时包含武器、弹药、misc**)时,对每一件装备无差别调用 `getType().hasFlag(MiscType.F_TOOLS)`。当某件是武器时,就是拿 `MiscTypeFlag` 去查 `WeaponType` → 触发警告。
- 功能其实正确(返回 false 合乎预期),纯日志噪音;但会淹没真正有用的日志。

**修复**
`Infantry.setSpecializations` 内 4 处同源写法(TRENCH / DEMO 工兵各"添加/移除"两处),统一先用 `instanceof MiscType` 收窄再查 misc 标志:
```java
.anyMatch(m -> m.getType() instanceof MiscType misc
      && misc.hasFlag(MiscType.F_TOOLS)
      && misc.hasFlag(MiscTypeFlag.S_DEMOLITION_CHARGE));
```
`:megamek:compileJava` 通过。语义不变(这些检查本就只应匹配工具类 misc 装备)。

**通用工程约定(避免复现)**
- `WeaponType`、`MiscType`、`AmmoType` **三者都**重写了 `hasFlag(EquipmentFlag)` 并做严格类型检查(分别见 `WeaponType.java:880`、`MiscType.java:407`、`AmmoType.java:2355`):**传错标志类型 = 警告 + 返回 false**。
- 因此:凡是拿到一个可能是任意子类型的 `EquipmentType`/`getType()`(尤其是遍历 `getEquipment()` 这种混合了武器/弹药/misc 的集合),**在调用类型特定标志前必须先 `instanceof` 收窄**:
  - 查 `MiscTypeFlag`(含 `F_*` / `S_*`)前 → `instanceof MiscType`
  - 查 `WeaponTypeFlag` 前 → `instanceof WeaponType`
  - 查 `AmmoTypeFlag` 前 → `instanceof AmmoType`
- 排查此类警告的最快方法:在 `megamek.log` 里读那条警告后面的 `Throwable` 堆栈,它会直接指出**误调用的代码位置**——通常不在装备类自身,而在遍历装备的上层逻辑里。

## 2026-07-09 — OS HVAC 去除 IS 版殉爆机制(改为电磁化学能自动炮)

**背景**
OS HVAC(Improve/Enhanced HVAC/12-18)此前 `extends HVACWeapon` 并 `explosionDamage = damage`,完整继承了 IS HVAC 的殉爆。设计上 OS HVAC 是电磁化学能自动炮,与 IS 版是两款不同武器,不应殉爆。

**殉爆的两个来源(都已处理)**
1. 暴击殉爆:`EquipmentType.isExplosive` 对 `instanceof HVACWeapon` 且有弹药者判为可爆;根源是 `ACWeapon` 构造里 `explosive = true`。**光删 `explosionDamage` 不够**,必须把 `explosive` 置回 false。
2. 掷骰天然 2 殉爆:`HVACWeaponHandler.doChecks` 会卡壳+摧毁+`explodeEquipment`。

**修复(代码)**
新增基类 `weapons/autoCannons/outerSphere/OSHVACWeapon extends HVACWeapon`:构造里 `explosive = false; explosionDamage = 0;`,并 `getCorrectHandler` 改用 `ACWeaponHandler`(跳过 HVAC 的掷骰-2 殉爆,沿用 `OSHyperLaserHandler` 那种"OS 版继承祖父 handler 去惩罚"的既有模式)。8 个 OS HVAC 类改为 `extends OSHVACWeapon`、删除各自的 `explosionDamage = damage;`、去掉冗余 import。`:megamek:compileJava` 通过。

**待定(命名/描述)**
把 OS HVAC 正式定性为"电磁化学能自动炮"的英文命名与描述文案待用户确认后统一落地(display name 是否改动涉及既有设计 .mtf 向后兼容——如 `Atlas ASX` 引用 "Improve HVAC/12")。javadoc 已临时改为 "electromagnetic-chemical action — no cook-off";Enhanced 的 "refined electrothermal" 措辞待与最终术语统一。

## 2026-07-09 — 单位选单里 IS/Clan 高等级条目消失(技术等级上限不一致)

**现象**
MM 大厅"选择单位"的技术等级列表里,IS/Clan 的 Advanced / Experimental / Unofficial 六个条目消失,而 OS、Ascended 条目照常显示。

**根因(不一致的 bug)**
`AbstractUnitSelectorDialog.updateTypeCombo()` 用 `gameTechLevel` 算出 `maxTech`,再以 `for tl in 0..maxTech` 生成 IS/Clan 条目;`MegaMekUnitSelectorDialog.updateOptionValues()`(第 90 行)把 `gameTechLevel` 取自游戏的 `techlevel` 选项。当这局技术等级低于 Unofficial 时,`maxTech` 被砍(如 Standard→T_TW_ALL=4),高等级 IS/Clan 条目就不生成。而紧随其后的 OS/Ascended 块是"无视上限总是添加"——于是 OS/Ascended 在、IS/Clan 高等级不在,产生不一致。(MML 与主菜单浏览器把 gameTechLevel 硬编码为 Unofficial,所以那边一直全显示。)

**修复(代码)**
把 `updateTypeCombo()` 里的 `maxTech` 恒设为 `TechConstants.T_CLAN_UNOFFICIAL`,让 IS/Clan 全部等级与 OS/Ascended 一样**总是列出**。年代/canon/合法性过滤仍照常生效,只是让所有技术等级在选单里可选。`:megamek:compileJava` 通过。

**注意(独立的第二层)**
条目"是否被勾选"由保存的 `MekSelectorRuleType` 决定;若此前只勾了一个等级(如 `[1]`),修复后条目会出现但默认未勾选,需要在列表里选中(或后续把默认选择也改为全选)。

## 2026-07-09 — MML 自定义设计存进 data/ 目录,MM 看不到(保存目录漂移)

**现象**
在 MM 选单里搜不到最新设计(例:`Atlas ASX-OS/T`、`Atlas ASX-OS/T HVAC/12`),关键字搜索无任何结果——不是被过滤,是根本没进 MM 缓存。

**根因**
这两个设计被存到了 `megameklab/megameklab/data/mekfiles/`(MML 自己的 data 目录),而非两边共享的 UserDir(`megamek/megamek/userdata/mekfiles`)。MM 只扫描自己的 `data/mekfiles` + 共享 UserDir,**从不扫描 megameklab 下的目录**,所以看不到。
为什么存到那里:`MMLFileChooser` 构造时默认目录取自 `CConfig.FILE_LAST_DIRECTORY`(上次使用的目录)。之前浏览/保存漂移到了 `data/mekfiles`,新设计就默认存进那个"上次目录"。而 `data/` 是构建时从 mm-data staging 覆盖的目录,把自定义单位放这里既对 MM 不可见、又可能被 clean 重建冲掉。

**修复(代码)**
`megameklab/.../ui/util/MegaMekLabFileSaver.java` 的 `chooseSaveFile`:当保存对话框的记忆目录为空、或位于**打包的 `data/` 树内**时,默认改到共享 UserDir(`ClientPreferences.getUserDir()`,正是 MM 扫描单位的位置);其它情况保留记忆目录。这样新设计默认落到 MM 能读到的地方。`:megameklab:compileJava` 通过。
已存在的 2 个 ASX 文件手动移动到共享 UserDir,并清除两侧 `units.cache` 触发重扫。

**约定(避免复现)**
自定义单位一律存进 UserDir(共享),**绝不要存进任何模块的 `data/mekfiles`**(那是从 mm-data staging 出来的只读性数据,MM 不当作用户内容扫描,且会被构建覆盖)。排查"MML 有、MM 没有"的设计时,先确认文件是否落在共享 UserDir。

## 2026-07-09 — 步兵专精代码对武器误用 MiscType 标志(WeaponType.hasFlag 警告刷屏)

**现象**
`gradlew clean` 后启动 MegaMek,加载单位缓存(`Mek Cache Loader`)时 `megamek.log` 反复刷:
```
WARN [megamek.common.equipment.WeaponType] Incorrect flag check: tested MiscTypeFlag instead of WeaponTypeFlag
```
每加载一个含相关装备的步兵单位就触发一批。

**根因(注意:不是 OS 武器代码的问题)**
- 本轮 OS 提交给 `WeaponType.hasFlag(EquipmentFlag)`(`WeaponType.java:880`)新增了**严格类型检查**:传入的不是 `WeaponTypeFlag` 就打警告 + `Throwable` 并返回 `false`。这个检查**暴露**了一个既有 bug,并非引入它。
- 既有 bug 在 `Infantry.setSpecializations`(`megamek/common/units/Infantry.java`):遍历 `getEquipment()`(**同时包含武器、弹药、misc**)时,对每一件装备无差别调用 `getType().hasFlag(MiscType.F_TOOLS)`。当某件是武器时,就是拿 `MiscTypeFlag` 去查 `WeaponType` → 触发警告。
- 功能其实正确(返回 false 合乎预期),纯日志噪音;但会淹没真正有用的日志。

**修复**
`Infantry.setSpecializations` 内 4 处同源写法(TRENCH / DEMO 工兵各"添加/移除"两处),统一先用 `instanceof MiscType` 收窄再查 misc 标志:
```java
.anyMatch(m -> m.getType() instanceof MiscType misc
      && misc.hasFlag(MiscType.F_TOOLS)
      && misc.hasFlag(MiscTypeFlag.S_DEMOLITION_CHARGE));
```
`:megamek:compileJava` 通过。语义不变(这些检查本就只应匹配工具类 misc 装备)。

**通用工程约定(避免复现)**
- `WeaponType`、`MiscType`、`AmmoType` **三者都**重写了 `hasFlag(EquipmentFlag)` 并做严格类型检查(分别见 `WeaponType.java:880`、`MiscType.java:407`、`AmmoType.java:2355`):**传错标志类型 = 警告 + 返回 false**。
- 因此:凡是拿到一个可能是任意子类型的 `EquipmentType`/`getType()`(尤其是遍历 `getEquipment()` 这种混合了武器/弹药/misc 的集合),**在调用类型特定标志前必须先 `instanceof` 收窄**:
  - 查 `MiscTypeFlag`(含 `F_*` / `S_*`)前 → `instanceof MiscType`
  - 查 `WeaponTypeFlag` 前 → `instanceof WeaponType`
  - 查 `AmmoTypeFlag` 前 → `instanceof AmmoType`
- 排查此类警告的最快方法:在 `megamek.log` 里读那条警告后面的 `Throwable` 堆栈,它会直接指出**误调用的代码位置**——通常不在装备类自身,而在遍历装备的上层逻辑里。

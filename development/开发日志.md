## 2026-08-03 — Lance Radar 随 GUI Scale 缩放修复（雷达自绘 + 大厅容器布局）+ 遗留问题清单

修上游拉来的大厅 Lance Radar "不随 GUI Scale 正确缩放 / 放大反而变小 / 重叠" 的一连串问题（多轮迭代）。

**雷达自绘（`LanceRadarChart`）**：
- 绘制改为**固定逻辑画布 380×480 + 一次性统一 `g2.scale(k,k)`**（k=min(w/380,h/480)、居中）——整张图作为刚性整体等比缩放：布局/样式不变、绝不重叠、不变形；保留原"数值框围绕六边形"样式；字体度量改用组件级 `getFontMetrics`（逻辑空间）。
- `getPreferredSize()` 改为**每次按当前 GUI Scale 现算**（原来构造时 `setPreferredSize` 定死一次 → gs 变时被邻居挤小、方向反了）。

**大厅容器（`ChatLounge`，根因二）**：
- `sp.setDividerLocation(400)` 硬编码左栏宽度 → 改 `scaleForGUI(400)`。
- 左栏在固定窗口高度里竖直堆叠、高 gs 被挤压 → 把 `leftSide` 包进 `JScrollPane`（竖向按需/横向关闭）解除高度挤压。
- GUI Scale **即时生效**：`preferenceChange` 加 `GUI_SCALE` 分支，即时重设分隔位 + revalidate；`sp` 提为字段 `unitsSplitPane`。

**验证**：`:megamek:compileJava` 通过。**未 GUI 实测**；用户实测反馈"有进步、部分解决"。

**⚠️ 当前未解决问题（问题清单）**：
1. **左栏向右偏移**：包滚动面板/重设分隔位后左栏内容右移（疑 `FixedXPanel` 在视口靠左留空 / 竖向滚动条占位）；待用户截图定位。
2. **Unit Details 缩放 vs 拉伸**：`MekCardView` 的 Unit Details 是 HTML `JLabel`（文本+图标），字体随 gs 变大只会**重排**（=用户说的"拉伸"），Swing 文本无法等比"缩放"。待选：**A** 让其 `preferredSize` 随 gs 动态（面积正确缩放、文本仍重排，小改）；**B** 渲染成可缩放矢量/图片单位卡（MekBay 式，大改）。
3. **雷达等比黑边**：面板长宽比 ≠ 380:480 时两侧留边；要"填满"则会拉伸，二者不可兼得，待取舍。
4. 即时改 gs 会把分隔位**重置为缩放默认值**（覆盖用户手动拖动位置），如需保留比例再改。

**触及文件**：`LanceRadarChart.java`、`ChatLounge.java`、本日志。

## 2026-08-02 — 📌 下阶段方向定案：语义缩放 Force View + 派系底色=玩家色（设计决策，暂不开发）

大厅 MekBay 化的**下一阶段** = 把整个 **Force View 做成语义缩放(semantic zoom / 分级细节 LOD)** 的编制图——缩放级别决定"画什么、画多细",并在远端把下属部队塌缩成单个符号(既是美学也是性能刚需)。

**梯队阶梯(用户确认,8 级)**:Lance → Company → Battalion → **Regiment** → Brigade → Division → Corps → Army。
**LOD 渲染模式(按缩放带)**:
- 近端 **Lance/Company** = 单位自带贴图(+ 复用 Unit Details 配置数据),逐单位;
- 中端 **Battalion/Regiment** = **SLDF 权重级单位符号**(六边形/三角/菱形 + 权重填充 + 经验色环 + 派系底),逐单位;
- 远端 **Brigade→Army** = **梯队符号**(整支编队塌缩成一枚带梯队杠 |/||/||| 的符号),逐编队。
- 塌缩边界暂定营/旅之间;Regiment(~108 机)若逐单位太密,可后期把边界提前到团(单一阈值旋钮,不影响架构)。

**三组件在此框架下的含义**:
- **符号渲染器** = 一族按 LOD 切换的字形生成器(a 单位贴图[已有]、b SLDF 权重单位符号、c 梯队符号);
- **可缩放 TO&E 画布** = 递归树布局 + **语义缩放引擎(按 LOD 塌缩子树/切字形)** + AffineTransform 平移缩放 + 命中测试选择;核心大工程,先做只读、作新视图,保留 JTree 编辑;
- **交互式编组** = 画布上拖放调防/建散梯队/就地编辑;JTree 白送的 DnD/命中在自绘画布要全手写,最贵、最后。

**⚠️ 派系底色决策(重要,避免误攻坚)**:SLDF 符号底色**默认直接用玩家颜色**(`Player.getColour()`,现成),**不给 MegaMek 加"派系选择"功能**。理由:MegaMek 是桌游模拟器,玩家进来前**编成与阵营已在别处(MekHQ/纸面)决定好**;派系归属是 **MekHQ(战役层)的职责,不是 MegaMek 的刚需**。故此项**不作为攻坚对象**。
- 仅留作参考(若将来真要"家族旗色"):`Faction` 枚举 CC/LC/DC/FS/FW 已存在 → CC 绿(Liao)、LC 蓝(Steiner)、DC 红(Kurita)、FS 黄(Davion)、FW 紫(Marik)+ 其它/雇佣兵 Neutral 灰。但**当前实现就用玩家色**,不引入 House 字段/选择 UI。

**可复用资产(本轮已建)**:类型形状 `superCategory/subCategory`、梯队 `echelonName`、番号 `generateForceName`、编队分类 `FormationBonusType.detect`、经验环 `SkillLevel`、贴图+camo 合成 `buildIcon/smallUnitIcon`、层级遍历 `MekTreeForceModel`。

**建议分期**:① 符号渲染器 b/c 两档(出图例验证)→ ② 只读可缩放 TO&E 画布(核心,多轮)→ ③ 交互式编组(最后)。

`megameklab/.../ui/util/MegaMekLabFileSaver.java` 的 `chooseSaveFile`:当保存对话框的记忆目录为空、或位于**打包的 `data/` 树内**时,默认改到共享 UserDir(`ClientPreferences.getUserDir()`,正是 MM 扫描单位的位置);其它情况保留记忆目录。这样新设计默认落到 MM 能读到的地方。`:megameklab:compileJava` 通过。
已存在的 2 个 ASX 文件手动移动到共享 UserDir,并清除两侧 `units.cache` 触发重扫。

**约定(避免复现)**
自定义单位一律存进 UserDir(共享),**绝不要存进任何模块的 `data/mekfiles`**(那是从 mm-data staging 出来的只读性数据,MM 不当作用户内容扫描,且会被构建覆盖)。排查"MML 有、MM 没有"的设计时,先确认文件是否落在共享 UserDir。

## 2026-07-09 — 步兵专精代码对武器误用 MiscType 标志(WeaponType.hasFlag 警告刷屏)

**现象**
`gradlew clean` 后启动 MegaMek,加载单位缓存(`Mek Cache Loader`)时 `megamek.log` 反复刷:
```
WARN [megamek.common.equipment.WeaponType] Incorrect flag check: tested MiscTypeFlag instead of WeaponTypeFlag
```
每加载一个含相关装备的步兵单位就触发一批。

**根因(注意:不是 OS 武器代码的问题)**
- 本轮 OS 提交给 `WeaponType.hasFlag(EquipmentFlag)`(`WeaponType.java:880`)新增了**严格类型检查**:传入的不是 `WeaponTypeFlag` 就打警告 + `Throwable` 并返回 `false`。这个检查**暴露**了一个既有 bug,并非引入它。
- 既有 bug 在 `Infantry.setSpecializations`(`megamek/common/units/Infantry.java`):遍历 `getEquipment()`(**同时包含武器、弹药、misc**)时,对每一件装备无差别调用 `getType().hasFlag(MiscType.F_TOOLS)`。当某件是武器时,就是拿 `MiscTypeFlag` 去查 `WeaponType` → 触发警告。
- 功能其实正确(返回 false 合乎预期),纯日志噪音;但会淹没真正有用的日志。

**修复**
`Infantry.setSpecializations` 内 4 处同源写法(TRENCH / DEMO 工兵各"添加/移除"两处),统一先用 `instanceof MiscType` 收窄再查 misc 标志:
```java
.anyMatch(m -> m.getType() instanceof MiscType misc
      && misc.hasFlag(MiscType.F_TOOLS)
      && misc.hasFlag(MiscTypeFlag.S_DEMOLITION_CHARGE));
```
`:megamek:compileJava` 通过。语义不变(这些检查本就只应匹配工具类 misc 装备)。

**通用工程约定(避免复现)**
- `WeaponType`、`MiscType`、`AmmoType` **三者都**重写了 `hasFlag(EquipmentFlag)` 并做严格类型检查(分别见 `WeaponType.java:880`、`MiscType.java:407`、`AmmoType.java:2355`):**传错标志类型 = 警告 + 返回 false**。
- 因此:凡是拿到一个可能是任意子类型的 `EquipmentType`/`getType()`(尤其是遍历 `getEquipment()` 这种混合了武器/弹药/misc 的集合),**在调用类型特定标志前必须先 `instanceof` 收窄**:
  - 查 `MiscTypeFlag`(含 `F_*` / `S_*`)前 → `instanceof MiscType`
  - 查 `WeaponTypeFlag` 前 → `instanceof WeaponType`
  - 查 `AmmoTypeFlag` 前 → `instanceof AmmoType`
- 排查此类警告的最快方法:在 `megamek.log` 里读那条警告后面的 `Throwable` 堆栈,它会直接指出**误调用的代码位置**——通常不在装备类自身,而在遍历装备的上层逻辑里。

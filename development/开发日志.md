## 2026-08-01 — 完成 Kestrel / Shrike / Lodestar 网络目标指示器机制(§9.6)

把 §9.6 三件指示器从"空壳"接线为可用机制(编译 + AmmoType/EquipmentType 测试通过,**未实战测试**)。

**Kestrel(被动网络 -1)**:无需开火。`ComputeToHit` 调 `OSNetworkDesignators.hasNetworkKestrelPaint`——攻击者所在活跃 C3 网络中(含攻击者自己)有单位装可用 Kestrel,且该 Kestrel 在射程内"点亮"目标(有 LOS,或目标身上有友方 Lodestar 信标)→ 全网直射 -1。排除间接火力与火炮。

**Shrike(-1 / -3,可暴击)**:新建 `ShrikeTAGHandler`(继承 `TAGHandler`),命中时除标准 TagInfo 外,把"被 Shrike 指示 + 是否暴击(2d6 原始 ≥9)"写到目标(`Entity.shrikeDesignatedBy` / `shrikeDesignationCrit`,`newRound` 重置);`OSShrikeDesignator.getCorrectHandler` 改用它;`ComputeToHit` 经 `OSNetworkDesignators.shrikeToHitBonus` 读取,同网络攻击者 -1(暴击 -3)。Shrike 是 TAG,OFFBOARD 阶段结算,早于 FIRING,故开火时指示状态已就绪。

**Lodestar(Narc 信标弹)**:新增 `Munitions.M_LODESTAR`(**追加到枚举末尾**以保持既有 ordinal 稳定)+ `INarcPod.LODESTAR` 类型;`NarcHandler` 增分支,命中后 `attachINarcPod`(队伍所属,像普通 Narc pod 持续附着);弹药 `createOSLodestarAmmo`(OS Munin/iNarc,4 发,12000)已注册。Kestrel 的"信标在射程内"路径读取它(`pod.type()==LODESTAR && pod.team()==Kestrel 方`),免 LOS 给 -1。

**已解决的设计待定**:Lodestar 定为 Improve、走 Munin(iNarc)新弹种、成本 12000、像 Narc 一样持续。

**仍 TODO(§9.5)**
- **Lodestar 的 LRM 间接火力使能**:让 Kestrel 网络的 LRM 无需常规 spotter 即可对被信标目标间接开火——独立的间接火力合法性改动(`WeaponAttackAction` isIndirect / spotter 查找),本轮未接。
- **反叠加上限**:Kestrel/Shrike 的网络 -1 目前各自独立生效,尚未与 B-2500 协同 -1 / Improve C3 Point -1 共享"网络协同 -1"上限。

**坑/注意**
- `MRMWeapon` 不按弹种分派 handler(见前一条 MRM 记录);而 `NarcHandler` 是按 `AmmoTypeEnum` + munitionType 分派的,加一个 iNarc 弹种只需在 INARC 分支里加一段并新增 `INarcPod` 类型常量,通用附着/持久化机制自动复用。

- 未加 to-hit 专项单测(需构造含 C3 网络/LOS 的 Game,成本高);机制正确性留待游戏内 playtest。

## 2026-07-31 — 记录:车辆装能量武器的构造规则 + 车辆不能装 DHS(代码事实,正史存疑)

排查"OS 引擎开放给车辆"时,顺带确认了 MegaMek 里**车辆装能量武器**的构造规则(权威落地在校验器/实体类)。留档以备后用:

**1. 功率放大器(Power Amplifier)——非聚变引擎才需要。** `Entity.getPowerAmplifierWeight()`(`:14460`):聚变/裂变引擎返回 0;非聚变(ICE/燃料电池等)装能量武器(激光/PPC/等离子/喷火器 + PPC 电容)时,重量 = 能量武器总吨位 ×10%,向上取整到 0.5 吨。**与 OS 引擎的关联**:OS Improve ICE / Hybrid 已被设为 `isFusion()==false`,故会自动正确计收功率放大器;OS 聚变引擎不需要。

**2. 车辆"热中性" + 只能单散热器。** `TestEntity.calcHeatNeutralHSRequirement()`(`:976`)+ `TestTank.getCountHeatSinks/getWeightHeatSinks`(`:254`):车辆必须携带足够散热器,散尽全部**不吃弹药的能量武器**的热量(PPC 电容 +5、激光绝缘体 −1,最低 1);引擎免费散热器先抵扣,其余每个 1 吨。

**3. 车辆不能装 DHS(本代码库事实)。** `TestTank.hasDoubleHeatSinks()` 硬返回 false(注释 "tanks can't have DHS"),`Tank.java` 无任何 DHS 处理,散热器一律按单散热器计重。**⚠️ 正史层面存疑**:无法确认这是 TechManual 的硬规则还是 MegaMek 的建模取舍;且 BT 构造规则通常**不给 in-universe 解释**,所以未必存在"正史解释"。"DHS 更笨重、车辆内部空间容纳不下"是规则讨论里常见的**推测性**说法,非官方定论。以 TechManual "Combat Vehicles" 构造章为准。若 OS 想让车辆用 DHS,需改 `hasDoubleHeatSinks` + 散热器计重/计数逻辑。

## 2026-07-31 — OS 装甲线全面开放给车辆/战机 + 战机可用性严格对齐正史

**背景/需求**
用户要求把整条 OS 自定义装甲线(`ArmorType.java`,20 款 `createOS*`)从"机甲专属/部分开放"扩展到车辆与 Aerospace 战机,延续"OS 不做机甲专属"的原则。装甲可用性纯由机型 flag 门控:车辆 `F_TANK_EQUIPMENT`(`megameklab TankUtil:129` / `TestTank`)、支援车辆 `F_SUPPORT_TANK_EQUIPMENT`、VTOL `F_VTOL_EQUIPMENT`、战机 `F_FIGHTER_EQUIPMENT`。此前 OS 装甲只挂了部分 flag(FF 家族甚至只有 `F_MEK_EQUIPMENT`,故车辆装甲下拉里根本不出现)。

**改动 1:20 款全部补齐机型 flag。**
逐款锚定唯一的 `T_ARMOR_OS_*` 常量行,在其后追加一行实体 flag(第二个 `armor.flags = armor.flags.or(...)`)。这样避免与正史装甲相同的 flag 组合被误伤——正史 Hardened/Reactive 等有一模一样的 flag 行,若对 flag 行做 replace_all 会连正史一起改。

**改动 2:战机可用性严格按正史逐类对齐(关键教训)。**
起初图省事给全部 20 款都加了 `F_FIGHTER_EQUIPMENT`,用户纠正:应逐类镜像正史。核对正史后:
- **撤回(不给战机)**:**Ferro-Fibrous 全家族**(FF/Light/Heavy + Hardened-FF 复合)——战机走 Ferro-Aluminum,不用 FF;**Reactive**(正史 `ArmorType.java:836` 无 `F_FIGHTER`);**Hardened 及复合**(正史 Hardened `:948` 仅 Mek+Tank)。
- **保留(给战机)**:**Reflective**(正史 `:895` 有 `F_FIGHTER`)、**Ferro-Lamellor**(`:1038`)、**Ballistic-Reinforced** 与 **Anti-Penetrative Ablation**(正史二者均有 `F_FIGHTER`,`:1144`/`:1115`)。
- **Stealth**:保留 Mek+Tank+Fighter——偏离"正史 Mek-Stealth 仅机甲"的严格镜像,但有正史 *Vehicular Stealth*(`T_ARMOR_STEALTH_VEHICLE`,tank+fighter+vtol)先例 + 用户此前明确要求,故保留。

最终:8 款对战机开放(Reflective×2 / Ferro-Lamellor×2 / BRA / APA / Stealth×2),12 款不开放。

**教训**:镜像正史机型可用性要**逐类判断,别一把全开**;FF 是反例(战机专用 Ferro-Aluminum)。

**验证**:`:megamek:compileJava` 通过(仅既有 deprecation/unchecked 提示)。
**⚠️ 未实战测试 / 待补**:① 战机上装甲点数/吨位与临界槽分配——**正史给战机版设了 `fighterSlots`(Reflective=1、BRA=2 等),OS 版尚未设**,可能导致战机上护甲占位/成本不对,需补齐 `fighterSlots`/`svSlots` 后 playtest;② MML 里给车辆/战机建单时这些装甲能否正常选中→保存→回读。**触及文件**:`ArmorType.java`、本日志。

## 2026-07-31 — OS Hybrid 引擎技术等级 Advance→Standard + CCS 全面开放给车辆/支援车辆/战机

**改动 1:OS Hybrid 引擎技术等级 Advance → Standard(`Engine.java`)。**
用户要求把 OS Hybrid(内燃机 + 燃料电池混合)从 Advanced 降为 Standard。技术等级在两处独立系统里定义,都要改:
- **静态等级(现代 rules level,MML 显示/过滤用)**:`OS_HYBRID_TA.setStaticTechLevel(SimpleTechLevel.ADVANCED)` → `STANDARD`。
- **遗留 `getTechType(int year)`(`TechConstants.T_*` 旧式规则等级)**:Hybrid 原与 Improve ICE 等一组共用 `T_OUTER_SPHERE_ADVANCED`,现把 `OS_HYBRID_ENGINE` 拆出单独返回 `T_OUTER_SPHERE_STANDARD`(2800 年前仍 UNOFFICIAL,与其它 OS 引擎一致);Improve ICE 等其余引擎维持 Advanced。

教训:OS 装备的"技术等级"往往有**两套**表示(`SimpleTechLevel` 静态 + `TechConstants` 遗留年份法),改等级要两处一起改,否则 MML 与游戏内会不一致(Improve ICE 就是历史遗留的两处不一致:静态 STANDARD、遗留 ADVANCED)。

**改动 2:CCS(Combat Computer System)全面开放给非机甲机型(`MiscType.java`)。**
起因:用户发现 Combat Computer 与 Composite Targeting Computer 在 MML 里对车辆不可选。根因——CCS 五件装备(C-2500 核心、CC 弹道/能量/导弹模块、Composite TC)此前只打了 `F_MEK_EQUIPMENT`。车辆/战机可用性纯由 flag 门控:`megameklab TankUtil:129`(战车)、`TestTank:111`(校验器)查 `F_TANK_EQUIPMENT`,战机查 `F_FIGHTER_EQUIPMENT`,支援车辆查 `F_SUPPORT_TANK_EQUIPMENT`——无技术基线判定。
- **规则确认**:原版 Targeting Computer(`createISTargComp`/`createCLTargComp`)本就带 `F_MEK_EQUIPMENT + F_TANK_EQUIPMENT + F_SUPPORT_TANK_EQUIPMENT + F_FIGHTER_EQUIPMENT + F_HEAVY_EQUIPMENT`——即 TC 类装备在规则上对 Mek/战车/支援车辆/战机全开放。Aerospace 并非"没有 TC 类装备"。
- **用户拍板**:CCS 作为 OS 版 TC,没理由做成 Mek 专属("外天体没有必要设计一个只能装备在机甲上的系统")。给五件装备统一加 `F_TANK_EQUIPMENT, F_SUPPORT_TANK_EQUIPMENT, F_FIGHTER_EQUIPMENT`,与原版 TC 对齐(仅未加 `F_HEAVY_EQUIPMENT` 支援车辆重型标记,如需完全对齐可后补)。

**根因(注意:不是 OS 武器代码的问题)**
- 本轮 OS 提交给 `WeaponType.hasFlag(EquipmentFlag)`(`WeaponType.java:880`)新增了**严格类型检查**:传入的不是 `WeaponTypeFlag` 就打警告 + `Throwable` 并返回 `false`。这个检查**暴露**了一个既有 bug,并非引入它。
- 既有 bug 在 `Infantry.setSpecializations`(`megamek/common/units/Infantry.java`):遍历 `getEquipment()`(**同时包含武器、弹药、misc**)时,对每一件装备无差别调用 `getType().hasFlag(MiscType.F_TOOLS)`。当某件是武器时,就是拿 `MiscTypeFlag` 去查 `WeaponType` → 触发警告。
- 功能其实正确(返回 false 合乎预期),纯日志噪音;但会淹没真正有用的日志。

**修复**
`Infantry.setSpecializations` 内 4 处同源写法(TRENCH / DEMO 工兵各"添加/移除"两处),统一先用 `instanceof MiscType` 收窄再查 misc 标志:
```java
.anyMatch(m -> m.getType() instanceof MiscType misc
      && misc.hasFlag(MiscType.F_TOOLS)
      && misc.hasFlag(MiscTypeFlag.S_DEMOLITION_CHARGE));
```
`:megamek:compileJava` 通过。语义不变(这些检查本就只应匹配工具类 misc 装备)。

**通用工程约定(避免复现)**
- `WeaponType`、`MiscType`、`AmmoType` **三者都**重写了 `hasFlag(EquipmentFlag)` 并做严格类型检查(分别见 `WeaponType.java:880`、`MiscType.java:407`、`AmmoType.java:2355`):**传错标志类型 = 警告 + 返回 false**。
- 因此:凡是拿到一个可能是任意子类型的 `EquipmentType`/`getType()`(尤其是遍历 `getEquipment()` 这种混合了武器/弹药/misc 的集合),**在调用类型特定标志前必须先 `instanceof` 收窄**:
  - 查 `MiscTypeFlag`(含 `F_*` / `S_*`)前 → `instanceof MiscType`
  - 查 `WeaponTypeFlag` 前 → `instanceof WeaponType`
  - 查 `AmmoTypeFlag` 前 → `instanceof AmmoType`
- 排查此类警告的最快方法:在 `megamek.log` 里读那条警告后面的 `Throwable` 堆栈,它会直接指出**误调用的代码位置**——通常不在装备类自身,而在遍历装备的上层逻辑里。
